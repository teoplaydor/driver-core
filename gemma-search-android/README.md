# Смысловой поиск — прототип на EmbeddingGemma 2

Android-приложение, которое ищет **фото, видео и заметки по смыслу** прямо на телефоне.
Модель — [EmbeddingGemma 2](https://huggingface.co/onnx-community/embeddinggemma-2-ONNX) (Google DeepMind,
6 октября 2026, 740M: текст 270M + изображения 170M + звук 300M, Apache 2.0) в формате ONNX; движок —
ONNX Runtime (процессор, видеокарта через WebGPU, NPU через NNAPI). С 0.8 по желанию — ещё и движок Google
LiteRT-LM со своей сборкой той же модели. После загрузки модели всё работает офлайн, файлы никуда не
отправляются.

## Что умеет

- **LiteRT-LM** (0.8): Google выпустил EmbeddingGemma 2 сразу и в своём формате `.litertlm` для движка
  LiteRT-LM — на нём работает поиск по фото в Google AI Edge Gallery; видеокарту он гоняет своими
  мобильными ядрами (OpenCL/WebGPU), NPU для этой модели Google обещает через ML Kit. «Настройки →
  Скорость → Проверить LiteRT-LM и fp16» скачивает его библиотеки (AAR `litertlm-android` 0.18–0.19 из
  Google Maven, только arm64) и сборку модели из LiteRT Community на Hugging Face (вариант «текст +
  картинки», если есть, иначе 740M). Java-обвязка (`com.google.ai.edge.litertlm.*`) повторяет JNI-интерфейс
  LiteRT-LM 0.18 один в один; библиотеки грузятся по пути, сбой в нативном коде отключает вариант. Подбор
  сравнивает LiteRT-LM (видеокарта и процессор) с остальными: если его векторы совпадают с ONNX-версией
  (косинус ≥ 0,98), он просто становится ускорением; если отличаются, но он заметно быстрее — предлагается
  «Перейти на LiteRT-LM» с переиндексацией галереи и заметок (и «Вернуться на ONNX Runtime» обратно).
  Смешивать векторы двух сборок в одном индексе приложение не даёт. На Galaxy S26 Ultra (Snapdragon 8 Elite
  Gen 5) на 70 токенах LiteRT-LM и ONNX Runtime на видеокарте вровень (0,26 и 0,27 с на фото). Но сборка
  LiteRT-LM из LiteRT Community не принимает 280 токенов: она считает всё со своей детализацией (векторы при
  70 и 280 одинаковые), поэтому для «Максимальной» и для скриншотов в режиме «Авто» подбор её не выбирает.
- **fp16-внимание** (0.8.2): у ONNX-версии внимание уже слитое (`com.microsoft:MultiHeadAttention`, 16 слоёв),
  и ONNX Runtime 1.30 считает его на видеокарте flash-ядром; на 280 токенах это ~7× работы против 70 —
  1,5–2,4 с на снимок. Вариант «Видеокарта (WebGPU), int8 + fp16-внимание» оставляет 4-битные слои как есть,
  а каждое внимание оборачивает в Cast(fp16)/Cast(fp32) (маска сначала ограничивается −60000, в fp16 не
  помещается −3.4e38): видеокарты Adreno считают fp16 вдвое быстрее. Граф переписывает `OnnxPatcher`
  на телефоне, без докачки; что быстрее — решает подбор. На Galaxy S26 Ultra оно оказалось быстрее int8 на
  ~16% при 280 токенах (реально около 1,7 → 1,45 с на снимок).
- **NPU Snapdragon через Qualcomm QNN** (0.9, экспериментально): визуальная часть идёт на Hexagon NPU
  напрямую, а не через NNAPI. «Настройки → Скорость → Проверить NPU Snapdragon» (кнопка видна на
  Snapdragon) докачивает с Maven Central сборку ONNX Runtime с QNN (`onnxruntime-android-qnn` 1.29.0, её JNI
  совпадает с нашими классами 1.30 символ в символ) и `qnn-runtime` 2.42.0 (под неё собрана эта сборка), из
  которого остаются только HTP-бэкенд, компилятор графа, QnnSystem и stub/skel для Hexagon этого чипа (V81
  для SM8850), ≈72 МБ загрузки; плюс полная версия визуального энкодера, если её нет. Эта сборка ONNX
  Runtime — только процессор и QNN, без WebGPU, и в одном процессе с основной не уживается, поэтому NPU
  работает в отдельном процессе `:npu` (`NpuService`): пиксели и признаки ходят через отображённый в память
  файл, запросы — через Binder, у каждого вызова срок; падение драйвера роняет только этот процесс, и вариант
  отключается. Процесс живёт дольше объекта сервиса (после отвязки Android создаёт новый), поэтому
  загруженные библиотеки и окружение ONNX Runtime в `NpuService` статические — в 0.9.1 новый объект
  оставался без окружения. QNN не умеет `MultiHeadAttention` и `SimplifiedLayerNormalization`, поэтому `OnnxPatcher.forQnn`
  раскладывает их на простые операции (внимание — Reshape/Transpose/MatMul/Softmax, маска ограничена −60000
  для fp16; RMS-нормализация — по X, делённому на свой наибольший модуль: квадраты не больше 1 и не
  переполняют fp16, а ε входит как (√ε / масштаб)², потому что сам ε = 1e-6 ниже нормального диапазона fp16 и
  NPU его обнуляет — на нулевом векторе дополнения это давало 0/0 = NaN, и в 0.9.5 весь результат на NPU
  был NaN). Константы за пределами fp16 приводятся в его диапазон по тому, как используются: «заглушка»
  (±3.4e38, ±∞) в данных — маска, в том числе приписанная экспортом к ключам отдельным каналом (q·k
  тогда сразу содержит маску; так устроен экспорт Gemma 4 vision: головы q/k шире v на 4) — становится
  ±10⁴, этого хватает для маски и далеко до переполнения при сложении; граница Clip/Min/Max (у
  «обрезаемых» линейных слоёв Gemma 4 — ±∞) становится ±65504; крошечные ненулевые — наименьшим
  нормальным fp16. В 0.9.6 заглушка была ±60000, и на NPU Q·Kᵀ второго слоя уходил в бесконечность —
  это показал поиск места порчи. Тест считает переписанный граф целиком в
  fp16 (эталонный вычислитель ONNX на numpy) с нулевыми строками под маской и активациями ×3000 и
  сравнивает с fp32 — графу из 0.9.5 он ставит «не годится»; отдельный тест — блок Gemma 4 vision, как его
  строит экспорт (маска в ключах, «обрезаемые» слои, позиции и RoPE). Вся логика по позициям фрагментов —
  всё, что зависит от `pixel_position_ids` и не зависит от пикселей: признак дополнения (`== -1`, «все»,
  «не»), маска внимания, углы RoPE, позиционные эмбеддинги, целочисленные `Gather` — считается на процессоре
  в fp32 (`QnnBuild.positionOnlyNodes`; логические операции — как арифметика над 0/1 в double): в 0.9.7
  NPU посчитал маску пустой (в ключах на NPU не оказалось ни одного −10⁴ — это показал поиск места
  порчи), и даже в BF16 совпадение было лишь 0.92. Тест проверяет, что после переноса NPU не получает ни
  одного логического или позиционного целочисленного входа. Перенос через double невозможен для операций,
  у которых в процессорном ONNX Runtime 1.29 нет double-ядра — проверены все операции модели, таких четыре:
  NonZero, Erf, Resize, OneHot (QNN их и так не берёт), — они остаются как были; если ONNX Runtime всё же
  сообщит о недостающем ядре, узел возвращается и сборка повторяется сама. Целочисленный результат
  (деление позиций в индексах пулинга) следующий узел берёт только после приведения обратно к целому —
  иначе терялось бы отсечение дробной части (тест это ловит: без этого расхождение 8.5%). Контекст NPU загружается, только
  если прошёл сверку с процессором (рядом есть заметка о точности). Сама сборка в NPU-процессе защищена в несколько слоёв: перед ней картинка
  проходит граф на процессоре в fp32 с модулями всех тензоров, и узлы, через которые идут значения больше
  16000 (например, домножение пулера на √768 — сам код Gemma 4 предупреждает, что оно выходит за fp16),
  остаются процессору; после сборки признаки NPU сверяются с процессорными на той же картинке (совпадение
  ≥ 0.98), иначе — сборка в BF16 (диапазон fp32; QNN разрешает её на SoC с номером 88 и выше — если
  откажет, это будет видно), иначе — ошибка с поиском места порчи; а в работе снимок, на котором NPU
  выдал не числа, пересчитывается на процессоре. Если результат NPU всё же разойдётся с
  эталоном, подбор ищет место порчи: копия графа отдаёт наибольший и средний модуль каждого float-тензора
  (до 600), её считают NPU и процессор на той же картинке, и в отчёт идёт первый тензор, ставший на NPU
  бесконечным или NaN (с узлом, его входами и цепочкой узлов вверх по графу — со значениями маленьких
  констант и модулями на процессоре и NPU), и тензоры, выходящие за пределы fp16 даже в fp32. Граф компилируется под NPU на
  фиксированный размер (пачка 1, фрагменты по детализации) при первом запуске — до нескольких минут — и
  сохраняется контекстом QNN рядом с графом. Почему QNN не собрал граф, он пишет только в системный журнал
  (через подробный уровень журнала ONNX Runtime), поэтому NPU-процесс на время сборки читает свой журнал
  (`logcat --pid`, приложению свои строки доступны) и `QnnLog` вытаскивает оттуда: сколько узлов взял QNN и
  сколько частей, какие операции он отверг и почему, код ошибки сборки и его ошибки — отдельно те, что при
  сборке, и те, что при проверке отдельных узлов (такие узлы и так остаются процессору). Виновника сборки
  ищет `QnnBuild`: его называют ошибки QNN или, если не называют, бинарный поиск по графу — QNN собирает
  графы из первых k узлов (≈11 сборок), а перед поиском крошечный граф (MatMul → Add → Softmax) проверяет,
  собирает ли NPU хоть что-то (если нет — дело в доступе к NPU, а не в модели). Найденный узел во всех слоях
  считается в double (`OnnxPatcher.keepOnCpu`): QNN double не умеет, поэтому узел остаётся процессору, а
  вокруг него — приведения типов туда и обратно; типы и формы тензоров даёт сам ONNX Runtime (копия графа,
  где все тензоры объявлены выходами без типа). Назначение узлов по имени
  (`session.name_based_layer_assignment`) для QNN не годится: отфильтрованный граф прячет от QNN
  константы, и он падает на первом Slice. Каждый узел графа для QNN носит в имени уникальную метку
  (`_N12N`). Список узлов, оставленных процессору, сохраняется рядом с графом, и следующая сборка начинает с
  него. На всё — до 15 минут; ошибки первой попытки, описание виновника (типы и формы входов и выходов) и
  каждая попытка с её временем попадают в отчёт. В отчёт подбора
  идёт профиль: сколько узлов взял NPU и что осталось процессору, и как прошла сборка. Когда QNN есть, варианты через NNAPI больше не замеряются.
- **NPU на 280 токенах** (0.10): в 0.9.9 первая же фотография на максимальной детализации убивала NPU-процесс,
  а индексация считала каждый следующий файл ошибкой («0.09 с на файл», в индексе 0). Причина — замер модулей
  всех тензоров перед сборкой: ONNX Runtime упорядочивает узлы обходом вверх от последнего «листа» графа, а
  узлы замера стояли в конце, поэтому сначала считался весь граф и каждый тензор жил до конца прогона —
  энкодер размера Gemma 4 на 2520 фрагментах занимал 13 ГБ. Теперь `OnnxPatcher.withRanges` ставит замеры в
  обратном порядке, каждый тензор меряется сразу и освобождается: 1.3 ГБ (на 630 фрагментах 0.6 ГБ вместо
  1.8, и в 4–5 раз быстрее). Кроме того, сборка под новую детализацию берёт узлы для процессора из уже
  проверенной сборки другой (та же модель, другие размеры) и замер не делает вовсе; перед компиляцией QNN
  закрываются эталонные сессии процессора. Неудавшаяся сборка запоминается в процессе: следующий снимок
  получает ту же ошибку сразу, без новой сборки на минуты. NPU-процесс пишет в кэш, чем занят, с памятью
  процесса, а приложение после его падения добавляет к ошибке этот этап и запись Android о конце процесса
  (Android 11+: нехватка памяти, сбой в машинном коде, сигнал, память в конце). Перезапущенный Android'ом
  процесс без графа больше не используется.
- **Скан: все наклоны по отдельности** (0.10.25). По скану 0.10.24 (договор): линейки формы почти идеальны (0–2 пикс.
  от края до края), но текст по участкам наклонён на 2–8 пикс.: абзац 9.7, блок «ИНСТИТУТ…», левые концы строк
  центрированного абзаца, строка подписей. Причины и что сделано. *Строки текста принимались за линейки*: у шрифта
  с засечками ряд «ножек» букв так же полон, как линейка, — строки абзаца рвались на куски с ложным наклоном; теперь
  у линейки ещё и пусто в 2–3 рядах по обе стороны. *Положение строки* брали по середине самых полных рядов — оно
  прыгало на 1–2 пикс. от полосы к полосе; теперь середина полосы половинной высоты с долями пикселя (разброс
  втрое меньше). *Прописные и цифры* стоят выше строчных (середина на треть буквы выше) — слова «ОБУЧАЮЩИЙСЯ», номера
  ИНН/счёта сдвигались на 2–3 пикс.; теперь строка ведётся по линии, на которой стоят буквы (низ букв — общий у
  прописных, строчных и цифр); точка, где низ и середина не согласны («7», точка, обрезанная буква), не берётся.
  *Концы строк*: первое и последнее слово часто не попадали в свою полосу, а у загнутого угла трасса их теряла —
  концы уходили на 3–6 пикс.; теперь трасса доводится до самого края чернил по полполосы, точка ставится в центр
  чернил полосы, а не в её середину. *На наклонных участках* чернила считаются вдоль наклона строки (иначе низ букв
  читался ниже). *Остаточный проход* — по всем строкам (и тем, где гладкая поверхность промахнулась: у загнутого угла
  они важнее всего), сглаженно вдоль строки (локальная прямая, по весу чернил), а сдвиг строки держится на всю высоту
  её букв (строки разной длины больше не перекашивают буквы к соседней). *Куски одной строки* склеиваются по
  промежутку между трассами (чернила могли перекрываться), соседние полосы сравниваются напрямую. *Короткие строки*
  из пяти точек и такие же склейки молча терялись (парабола требует шести) — из списка с чекбоксами пропадали
  «Название МТИ», «Расположение», и колонка списка не выравнивалась; теперь через них прямая. *Кривая строки за
  концом трассы* больше не продолжается полиномом (кубика на загнутом договоре уводила строку на 70 пикс.), а идёт
  прямо. Вертикали и интервалы считаются по рядам, в которые строки лягут после выпрямления (средняя высота
  строки на изогнутом листе зависела от того, какую её часть удалось проследить); на ровном листе интервалы так
  выходят ровными до 1 %, и выравнивать их теперь начинаем с 3 % (было 5 %). Группа начал строк проходит через
  строки формы, разделённые линейкой. Загнутый внизу A4 больше не
  принимается за Letter (лист сплющивался): допуск A4 10 %, Letter убран; согнутый лист сверяется по площади внутри
  кривых краёв. `DocScanTest`: новый реалистичный кадр — страница договора (шрифт с засечками, абзац по ширине,
  реквизиты, форма с линейками, центрированный абзац, подписи), снятая телефоном 3000×4000, выгнутая, с волной,
  загнутым низом и наклоном: линейки ≤ 2 пикс. от края до края, текст ≤ 1.8 пикс. на треть ширины (было 6.5), края
  абзацев уходят ≤ 0.4 пикс., подписи — на одной высоте (±1 пикс., было 4.5). Мера краёв абзацев теперь считает
  только группы, уходящие больше чем на 2 пикс. (одно слово на 2 пикс. в группе из пяти строк — не наклон), и

  стали 1–2.

  общий процент и время, текущий этап с тем, что он делает сейчас (загрузка варианта, прогрев или сборка под
  NPU, замер 1 из 2; у NPU — ещё и шаг самого NPU-процесса раз в секунду: сборка под N фрагментов, способ,
  память процесса), и все этапы: готовые с результатом (время, совпадение, «расходится»), идущий с процентом
  и временем, ожидающие, пропущенные и не сработавшие. Лист можно закрыть — подбор идёт дальше, а строка
  вверху главного экрана и подсказка в настройках показывают процент и этап (нажатие открывает лист снова).
  Вес этапа — его ожидаемое время: в первый раз прикидка (первая сборка под NPU — минуты), потом время того же
  замера в прошлый раз на этом телефоне; внутри этапа процент идёт по частям (потоки, пачки, перемеры) и по
  времени — до 90% к ожидаемому, дальше медленно к 99%, так что этап не выглядит законченным раньше времени,
  а общий процент никогда не идёт назад (`StageProgress`).
- **NPU на 280 токенах, вторая попытка** (0.10.1): после 0.10 замер больше не мешал (пик 1.5 ГБ), но
  процесс падал в машинном коде уже в самой компиляции QNN (2.3 ГБ, не нехватка памяти). Большой граф
  (больше 1024 фрагментов) теперь собирается облегчёнными способами по очереди: внимание по частям вдоль
  запросов (`OnnxPatcher.chunkAttention`: Split запросов → своя MatMul → Softmax → MatMul на каждую часть →
  Concat; Softmax идёт вдоль ключей, так что результат тот же до бита — тест сравнивает и при неравных
  частях, — а самый большой тензор, оценки 12 × 2520², в 4 раза меньше), затем умеренная оптимизация QNN
  вместо третьей, затем граф на NPU в 4 и в 8 частях (Split одного из слоёв остаётся процессору — граница
  между частями). Перед каждым способом в заметке рядом с графом пишется «начат»; если процесс упал, следующий
  запуск записывает этот способ как уронивший процесс и берёт следующий. Подбор и индексация сами перезапускают
  NPU-процесс (до 3 раз; при индексации снимки возвращаются в очередь), так что все способы проходят за один
  запуск, а в отчёт идут все падения. О падении в машинном коде теперь видно, где оно: из tombstone Android
  (`ApplicationExitInfo.getTraceInputStream`, protobuf AOSP или текст) — сигнал, сообщение (например, о
  необработанном исключении C++), стек упавшего потока с библиотеками и функциями и последние строки журнала
  процесса (`Tombstone`). В отчёт подбора добавлен профиль самого QNN (`profiling_level=detailed`, отдельной
  сессией): время NPU по типам операций и самые долгие узлы — куда уходят 0.28 с на 70 токенах.
- **Индексацию не топит сломанная модель** (0.10): падение NPU-процесса останавливает прогон сразу, а
  одна и та же ошибка модели на 8 файлах подряд — после них; эти файлы не запоминаются как ошибочные
  (следующий запуск возьмёт их), а в статусе — причина. После падения NPU модель перезагружается (новый
  процесс), а фоновая индексация NPU не трогает, пока прогон не запустят вручную. Первая сборка NPU под
  детализацию видна в статусе и не портит «с на файл». Ошибка модели больше не переключает детализацию на
  максимальную: так делалось для энкодеров с одной зашитой детализацией, а любая ошибка на 70 токенах
  (например, падение NPU) молча переводила всю индексацию на 280.
- **Честный подбор** (0.8.3): на почти пустой батарее, в экономии или нагретым телефон считает в разы
  медленнее (замер на 9% заряда дал 7,1 с там, где обычно 1,7 с). Теперь отчёт начинается с условий
  (заряд, зарядка, экономия, нагрев), перед замером в таких условиях приложение предупреждает, эталонный
  прогон на процессоре идёт первым, за ним — вероятные победители, пока телефон холодный, NPU — последним;
  два лучших варианта (если они близки) перемериваются вперемешку, а повторный замер победителя показывает,
  замедлился ли телефон за время подбора.
- **Подбор и скриншоты** (0.8.1): с детализацией «Авто» победитель и самый быстрый вариант LiteRT-LM
  замеряются и на 280 токенах (после паузы на остывание), а выбор делается по среднему времени на снимок с
  учётом настоящей доли скриншотов в галерее. Подбор проверяет, что LiteRT-LM действительно меняет
  детализацию (векторы при 70 и 280 различаются) и насколько он совпадает с ONNX на той же детализации; если
  сборка не принимает нужное число токенов, это видно в состоянии модели. В отчёт добавлено устройство
  визуального энкодера (узлы, opset, как считается внимание, первый блок внимания по шагам), у окна отчёта
  есть «Скопировать».
- **fp16 для видеокарты** (0.8): та же кнопка докачивает `vision_encoder_fp16` из ONNX-репозитория.
  Мобильные видеокарты считают fp16 быстрее и гоняют вдвое меньше памяти; вариант «Видеокарта (WebGPU),
  fp16» участвует в подборе наравне с остальными. Неиспользуемые версии (fp16, LiteRT-LM, NPU) можно удалить.

- **NPU для EmbeddingGemma 2**: на одно фото около 85 % вычислений приходится на визуальный
  энкодер (он смотрит на 9 × детализация фрагментов картинки), остальное — на текстовую часть.
  Визуальный энкодер можно запустить на NPU через NNAPI: «Настройки → Скорость → Проверить NPU»
  докачивает его полную (fp32) версию — NNAPI не работает с 4-битной — и запускает подбор
  ускорения по всем вариантам: процессор, int8, видеокарта, NPU в fp16 и fp32, с разными пачками.
  Каждый вариант сверяется с эталонным прогоном на процессоре (косинус ≥ 0,98), остаётся самый
  быстрый из точных, отчёт показывается сразу. NNAPI компилирует граф только с фиксированными
  формами: он собирается под текущую детализацию и пачку, фото меньше бюджета и кадры видео
  дополняются пустыми фрагментами (модель их маскирует — результат совпадает до 1e-7, проверено
  тестом). Текстовая часть остаётся на процессоре в int8, поэтому ожидаемое ускорение — в 3–5 раз,
  если NPU принимает граф целиком; это покажет подбор на телефоне. Если драйвер NPU уронит
  приложение, этот вариант больше не пробуется. На первом проверенном телефоне (8 ядер) NNAPI
  проиграл видеокарте: 4,8–6,4 с на фото против 1,7 с у WebGPU int8 (8 потоков, пачка 2) при
  280 токенах — NNAPI берёт граф не целиком. Если NPU не выбран, его версию (≈0,7 ГБ) можно
  удалить: «Настройки → Скорость → Удалить версию для NPU».
- **Детализация «Авто»** (по умолчанию для новых установок): обычные фото — 70 визуальных токенов
  (630 фрагментов, вчетверо меньше работы визуальному энкодеру), скриншоты и сканы — 280, там
  мелкий текст решает, о чём картинка. Скриншоты узнаются по альбому (Screenshots, «Снимки
  экрана», сканы, документы) и имени файла. Пачка за один проход берёт фото одной детализации.
- **Что видеокарта отдаёт процессору**: подбор ускорения делает один прогон победителя с
  профилировщиком ONNX Runtime и пишет в отчёт, сколько узлов графа ушло на ускоритель, какие
  операции остались на процессоре и сколько времени они заняли, и сколько было пересылок между
  устройствами. Там же — время победителя при 70 и при 280 токенах.
- **Отчёт о сбоях**: если приложение закрылось неожиданно, при следующем запуске оно один раз
  покажет, на каком шаге и почему (исключение, сбой в нативном коде, нехватка памяти), с кнопкой
  «Скопировать отчёт». После двух сбоев подряд при загрузке модель не загружается автоматически.
- **SigLIP 2** (версия 0.6) пробовался как быстрая модель для фото: на реальных фото качество
  оказалось заметно хуже, и с 0.7 фото снова индексирует EmbeddingGemma 2. Код остался
  (`core/SigLip.java`), выбор в настройках скрыт.
- **Индексация, пока телефон не используется** (кнопка на первом экране или в настройках):
  работает только при выключенном экране — на зарядке или при заряде выше 50 %, без режима
  экономии и пока телефон не нагрелся. Как только экран включается — пауза; если телефон в руках
  дольше трёх минут, модель выгружается из памяти. Чтобы Android не гасил работу, это служба с
  тихим свёрнутым уведомлением, приложение просит снять для себя ограничения батареи и само
  продолжает после перезагрузки. Когда всё проиндексировано, служба останавливается, а новые фото
  дальше берёт обычная фоновая задача.
- **Галерея**: недавние фото и видео плиткой — колонки одной ширины, каждый снимок целиком в
  своих пропорциях (горизонтальные, вертикальные, скриншоты — без обрезки). Та же плитка
  показывает результаты поиска. Фильтры «Все / Фото / Видео / Заметки».
- **Просмотр внутри приложения**: фото раскрывается из плитки на весь экран, листается
  свайпом влево-вправо, увеличивается щипком и двойным касанием, закрывается свайпом вниз.
  Видео играет прямо там. Внизу — «Похожие», «Поделиться», «Открыть в…».
- **Новые фото индексируются сами, в фоне**: задача JobScheduler срабатывает, когда в
  MediaStore появляется фото, скриншот или видео (плюс страховочный запуск раз в 6 часов),
  только когда батарея не разряжена. Сначала без модели проверяется, есть ли что-то
  новое; только тогда модель загружается, обрабатывает новые файлы и выгружается, если
  приложение закрыто. Файлы, которые не удалось прочитать, фоновая задача больше не трогает
  (ручной запуск пробует их снова). Удалённые с телефона фото уходят из индекса.
  Выключается в настройках: «Новые фото — автоматически».
- **Поиск по галерее текстом**: «кот на диване», «закат на море», «скриншот с кодом».
  Текст и изображения лежат в одном векторном пространстве (768 чисел), поэтому запрос
  словами находит картинку на любом языке.
- **Поиск по видео**: из каждого ролика берутся 4 кадра, и они кодируются как одно видео.
- **Панель под пальцем**: полупрозрачная вертикальная панель справа (или слева — в настройках):
  настройки, фильтры «Все / Фото / Видео / Заметки», «+» для заметки и поиск внизу, под большим
  пальцем. Строка поиска выезжает вдоль нижнего края, лента занимает весь экран.
- **Поиск по фото**: значок картинки в строке поиска или «Поделиться → Найти похожее» из галереи.
- **Похожие**: долгое нажатие на плитку или кнопка в просмотре находит похожие фото, видео и заметки.
- **Заметки**: карточками в той же плитке, смысловой поиск по ним (запрос «как зайти в
  интернет дома» находит «пароль от Wi-Fi»). «+» → новая заметка, «Примеры» — демо-набор.
- **Matryoshka**: длину вектора можно уменьшить до 512, 256 или 128 и сравнить качество.
- **Детализация фото**: «Авто» (70 токенов для фото, 280 для скриншотов) или 70, 140, 280 для всех.

## Установка

1. Скачайте `SemSearch.apk` (arm64, Android 8.0 и новее) и разрешите установку из
   неизвестных источников.
2. На первом экране — **«Скачать модель»**. Лучше по Wi-Fi, загрузка докачивается после обрыва.
   Чтобы индексация шла быстрее: «Настройки → Скорость → Проверить NPU» (или «Подобрать самое
   быстрое», если NPU в телефоне нет).
3. **«Начать сейчас»** — первая индексация при открытом приложении (экран не гаснет), или
   **«Пока телефон не используется»** — то же самое незаметно, когда телефон лежит. Дальше новые
   фото добавляются в фоне сами.
4. Кнопка поиска внизу панели — пишите запрос; поиск начинается, пока вы печатаете.

Уже обработанные файлы при повторном запуске пропускаются. После обновления с 0.6 фото снова
индексирует EmbeddingGemma 2 (индекс SigLIP сбрасывается).

## Интерфейс

Одна тёмная тема в приглушённых серо-голубых тонах без резких контрастов, шрифт
[Manrope](https://github.com/sharanda/manrope) (OFL, `assets/fonts/`), иконки рисуются

вырастает из плитки и сворачивается в неё, нижние листы выезжают снизу. Все настройки
(модель, индексация, скорость, поиск, вид) — в одной панели, кнопка вверху боковой панели.

## Русские запросы к фото

Текст на любом языке модель понимает хорошо. А вот картинки она связывает с текстом
заметно лучше по-английски. Поэтому для фото и видео русский запрос дополнительно переводится
по встроенному словарю (`assets/ru_en_lexicon.txt`, ~600 слов, поиск по основе слова через
стеммер Snowball). Ищется сумма векторов «русский + английский». Перевод показывается в строке
результата: «кот на диване» → «cat on sofa». Режим — в настройках, раздел «Поиск»:

- русский + английский (по умолчанию);
- только английский;
- без перевода.

Заметки всегда ищутся по исходному тексту.

Кнопка **«Проверить качество поиска»** считает сходство русских и английских формулировок и то,
насколько выдача по фото совпадает с английским запросом в каждом режиме. Отчёт можно
скопировать.

## Скорость индексации

Главный рычаг — NPU для визуального энкодера (см. выше). Прямой доступ к NPU Snapdragon через
Qualcomm QNN не встроен: его библиотеки весят около 75 МБ; NPU используется через стандартный NNAPI.

Остальное (всё — в настройках):

- **Детализация** (раздел «Индексация») — главный рычаг. 70 токенов примерно вчетверо
  быстрее, чем 280; «Авто» даёт эту скорость обычным фото и сохраняет 280 для скриншотов.
- **Чтение**: фото берутся через системный сервис миниатюр (Android 10+), а следующее фото
  готовится, пока считается текущее.
- **Потоки процессора** (раздел «Скорость»): по умолчанию по числу быстрых ядер. Можно попробовать 3–4 или 6.
- Телефон греется и снижает частоты: на зарядке и в прохладе индексация идёт быстрее.
- **Ускорение** и кнопка **«Подобрать самое быстрое»** (раздел «Скорость»). Автоподбор
  замеряет на телефоне четыре варианта:
  - процессор (как раньше);
  - процессор с int8-вычислениями: 4-битным умножениям ставится `accuracy_level=4`, патч графа
    делает `OnnxPatcher`, веса не копируются;
  - видеокарту через WebGPU-провайдер ONNX Runtime (Vulkan);
  - видеокарту с int8.

  Для лучшего варианта он затем перебирает число потоков и размер пачки: 2 или 4 фото за один
  проход визуального энкодера, что лучше загружает видеокарту. Варианты, у которых результат
  расходится с обычным процессорным (косинус < 0,98), отбрасываются; самый быстрый сохраняется.
  Если драйвер видеокарты уронит приложение, при следующем запуске GPU отключается сам.

## Как устроено

```
запрос / фото / кадры видео
   │  HfTokenizer (tokenizer.json, BPE + byte fallback)   ImagePreprocessor (Gemma 4: патчи 16×16)
   ▼                                                       ▼
onnx/model_q4.onnx  ◄── image_features / video_features ── onnx/vision_encoder_q4.onnx
   │  sentence_embedding (768, L2-норма)
   ▼
IndexStore: SQLite + векторы в памяти, косинус по префиксу (Matryoshka)
```

- `src/.../core/`: платформенно-независимая часть (запускается и на обычной JVM):
  токенизатор, препроцессинг, ONNX-пайплайн, загрузка с Hugging Face.
- `src/.../core/SigLip.java`: SigLIP 2 (две ONNX-башни, предобработка как в transformers.js,
  выбор ускорителя).
- `src/.../app/`: Android без AndroidX: галерея-плитка (`MasonryView`), боковая панель (`Rail`),
  просмотр (`Viewer`, `PhotoView`), настройки (`SettingsPanel`), сравнение моделей
  (`CompareSheet`), быстрая модель и автопроверка (`FastModel`, `Engine.checkFast`), фоновая
  индексация (`AutoIndex`, `AutoIndexService`), индексация в простое (`IdleIndex`,
  `IdleIndexService`, `BootReceiver`), MediaStore, SQLite.
- Входы и выходы модели повторяют `EmbeddingGemma2Model` и `EmbeddingGemma2Processor`
  из transformers.js 4.3.1. Промпты взяты из карточки модели: запрос
  `task: search result | query: …`, документ `title: none | text: …`, медиа передаются
  без префикса.

## Ограничения прототипа

- Аудио (поиск по голосовым) пока не подключено: нужен порт log-mel признаков Gemma 4.
- Генеративной модели (Gemma 4 E2B, 1-битный Bonsai) для ответов «своими словами» пока нет.
  Сейчас это только поиск.
- «Пока телефон не используется» срабатывает при выключенном экране; телефон, включённый, но
  лежащий на главном экране, от активного использования без особого доступа к статистике
  использования не отличить, поэтому в это время индексация не идёт.
- Некоторые оболочки (MIUI, EMUI и др.) сами завершают фоновые службы: если индексация ночью
  обрывается, в настройках приложения разрешите автозапуск / работу без ограничений.
- APK подписан отладочным ключом.

## Сборка без Android Studio

```bash
sudo apt install android-sdk-build-tools android-sdk-platform-23 dalvik-exchange zipalign apksigner openjdk-21-jdk
./build.sh          # → build/SemSearch.apk
./test/run_tests.sh # проверки выше (нужны python3, node, maven, JDK 21)
./test/robolectric4/run.sh UiShots   # только скриншоты экранов → build/shots/
```

Манифест линкуется с таблицей ресурсов Android 14 (типы foreground-служб), которую `build.sh`
извлекает из android-all Robolectric с Maven Central (4 МБ остаются в кэше).
ONNX Runtime 1.30 берётся с Maven Central. Нативные библиотеки — из AAR, а Java API
пересобирается из исходников в байткод Java 8 (`tools/patch_ort.py`), чтобы его принял `dx`.
